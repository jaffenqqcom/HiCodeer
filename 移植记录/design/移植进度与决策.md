## 待决策点

1. **hap 基类与 Index.ets 形态**：已定用 gpui-template 骨架（`RustAbility`，`defaultPage=true`），`moduleName` 已改为 `zed`。Index.ets 仍为 Hello World 占位，XComponent surface 是否自动传递需编译验证后确定。
2. **键盘映射**：feat 的 `gpui_ohos/src/ohos/keyboard.rs` 仍是 no-op，Zed 编辑器需要硬件键盘，需补 OHOS 键码 → GPUI `Keystroke` 映射。
3. **平台能力缺口**：剪贴板、菜单、URL、凭据、系统通知、文件选择器在 fork 的 `OhosPlatform` 中仍为空实现，Zed 应用层用到需补。
4. **进程创建**：git、language server、extension host、终端依赖 `std::process::Command`（沙箱禁 fork/exec），需线程替代 / 原生子进程 / SSH 桥。
5. **文件系统沙箱**：`paths` crate 目录映射（config/extensions/languages/database/logs → filesDir/cacheDir/tempDir）。已同步 `temp_dir` 一条（返回 `data_dir().join("cache")`），其余目录未映射。
6. **日志重定向**：`zlog` / `ztracing` 写文件路径在 OHOS 不可用，需重定向 hilog。
7. **版本差异影响**：已按本地 1.17.0 新版 trait 面适配完成同步，但编译未验证（rustup 工具链损坏）。
8. **pthread 符号桩（lib.rs）**：`pthread_mutexattr_setrobust` / `pthread_mutex_consistent` 返回 0，是链接期符号覆盖（feat 原样）。若依赖 robust mutex 的库真的用到会静默失败；需确认其在 OHOS 链接中的必要性。
9. **lib.rs 非 ohos 分支空函数**：`openharmony_app_not_available() {}` 是空函数，与「禁止空函数」规则冲突（feat 原样），建议删除或改为有实质行为。
10. **`[lib] crate-type = ["cdylib", "rlib"]`**：桌面构建会额外产出 cdylib 产物（feat 也如此），是否接受。
11. **sandbox crate 阻塞风险**：本地 `main()` 的 `sandbox::run_sandbox_launcher_if_invoked()` 无 ohos gate，`crates/sandbox` 核心逻辑 `#[cfg(target_os = "linux")]` 在 ohos 下会被编译，可能成为 ohos 构建阻塞点，需单独处理。
12. **denoise 依赖缺失**：feat 的 audio 有 `denoise = { path = "../denoise" }`（依赖 `crates/denoise`），本地无此 crate 也无引用。若需恢复降噪功能需引入。
13. **settings_ui 的 cpal 版本缺口**：本地 `settings_ui/src/pages/audio_input_output_setup.rs` 与 `audio_test_window.rs` 直接用 `cpal::DeviceId`，OHOS 下编译会失败。需决策：OHOS 排除这两个页面 / 按 feat 重写 / OHOS 构建排除 settings_ui crate。
14. **div.rs 例外**：`paint_scroll_listener` 的 `should_handle` 扩展替换了 1 行已有代码（非 OHOS 行为逐位一致），是「只增不改」纪律的唯一例外。
15. **编译验证**：rustup 工具链（1.97.1）损坏，三个 agent 均无法执行 `cargo check`。需在健康工具链下对 `crates/gpui`、`crates/zed` 做 ohos target 编译确认。

### git 依赖浅拉取（省存储）

- **背景**：cargo 的 git 依赖下载不支持 `--depth=1`，全量拉历史（tree-sitter-typescript 占 152MB）。手动 `git fetch --depth=1` 到 cargo db 缓存秒级完成。
- **脚本**：`/tmp/git_deps_parallel.sh` 8 路并行、每仓库 `--depth=1` 拉目标 commit 到 `refs/commit/<sha>`、多轮自愈直到全部就绪。30 个 git 依赖全部缓存完成（`cargo fetch --locked` 验证通过，去掉 `--locked` 后成功）。

### 依赖固化（patch 机制）

- **nix 0.29.0**：OHOS 下 2 处 cfg 判断缺失（`cmsg_len`、`ptrace Request` 类型不匹配）+ 3 处 dead_code（`GetU8`/`SetU8`/`GetCString`）。官方 0.29 无后续 patch 版。方案：全量复制到 `patches/nix/`，修复 cfg 后根 `Cargo.toml` `[patch.crates-io] nix = { path = "patches/nix" }` 固化。
  - `patches/nix/src/sys/socket/mod.rs`：`cmsg_len` cfg 排除 `target_env = "ohos"`（OHOS 的 `cmsg_len` 字段是 u32，与 musl 同布局）。
  - `patches/nix/src/sys/ptrace/linux.rs`：`Request` repr 归入 `i32` 组（加 `target_env = "ohos"`）。
  - `patches/nix/src/sys/socket/sockopt.rs`：3 个 struct 加 `#[cfg_attr(target_env = "ohos", allow(dead_code))]`。
- **openharmony-ability**：从 git 依赖转本地 path 副本，便于后续修改。
  - 全量复制到 `crates/openharmony-ability/`（非 patches，因属于 workspace 结构更合理）。
  - `crates/ability/Cargo.toml`、`crates/derive/Cargo.toml`：`workspace = true` 依赖改为显式版本（因作为独立 crate 引入，无法从自身 workspace 解析）。
  - 引用方改为 path：`crates/gpui/Cargo.toml`、`crates/gpui_ohos/Cargo.toml`、`crates/zed/Cargo.toml`。

### gpui_ohos 适配 zcoder 1.17 trait API

gpui_ohos 从上游 zed 1.3 同步，与 zcoder 1.17 的 gpui trait 有 API 差异。原则：**功能全保留，只改 API 形式**。

- `crates/gpui_ohos/src/ohos/platform.rs`：
  - 补 `on_system_wake` 实现（1.17 `Platform` trait 仍要求，E0046）。
  - `quit()` 的 `app.exit(0)` 改为 `log::warn!`（`OpenHarmonyApp` 无 `exit` 方法，E0599；OHOS 应用退出由系统管理）。
- `crates/gpui_ohos/src/ohos/dispatcher.rs`：
  - `get_all_timings`/`get_current_thread_timings` 移出 `impl PlatformDispatcher`（1.17 trait 已删，E0407），改为 `impl OhosDispatcher` 自有 `pub fn`；`ThreadTaskTimings` 构造补 `stats: TaskStatistics::default()`（E0063）。

## 依赖隔离重构（待办，最后实施）

**目标**：让 zed 和 gpui 的原生代码只依赖 `gpui_ohos`，不再直接依赖 `openharmony-ability` 等 OHOS crate（**运行时层面**）。OHOS 依赖只被 gpui_ohos 依赖。当前阶段二任务（键盘映射、IME 迁移等）优先，本项放最后。

### 现状（依赖泄漏点）

- **gpui**：
  - `crates/gpui/src/platform.rs:168`：`set_ohos_app(&self, _app: openharmony_ability::OpenHarmonyApp)`（Platform trait 签名）
  - `crates/gpui/src/app.rs:227`：`with_ohos_app(self, app: openharmony_ability::OpenHarmonyApp)`（Application 方法）
  - `crates/gpui/Cargo.toml` ohos 段声明 `openharmony-ability`
- **zed**：
  - `crates/zed/src/lib.rs:22-28`：`#[ability] openharmony_app(app: OpenHarmonyApp)`（NAPI 入口，宏 + 类型）
  - `crates/zed/src/main.rs:81,101-102,218-240`：`OHOS_ENTRY_APP` / `run_with_ability_entry` / `set_ohos_entry_app` / `with_ohos_app`
  - `crates/zed/Cargo.toml` ohos 段声明 `openharmony-ability`、`openharmony-ability-derive`、`napi-ohos`、`napi-derive-ohos`；`[build-dependencies] napi-build-ohos`

### 方案 B（re-export，推荐）

1. **gpui_ohos**：`pub use openharmony_ability::*;` + `pub use openharmony_ability_derive::ability;`（必要时 re-export `napi-ohos`/`napi-derive-ohos`）
2. **改 derive 宏**（`gpui_ohos/depend/openharmony-ability/crates/derive/src/lib.rs`）：生成代码的 `openharmony_ability::` 绝对路径改为 `::gpui_ohos::openharmony_ability::`（或支持 crate 路径参数）
3. **zed**：改 `use gpui_ohos::OpenHarmonyApp` + `use gpui_ohos::ability`；去掉 Cargo.toml 的 `openharmony-ability`、`openharmony-ability-derive`（运行时）
4. **gpui**：`set_ohos_app`/`with_ohos_app` 参数改为 `Box<dyn Any + Send + Sync>`（Any 擦除）或 gpui 自有 marker trait（如 `OhosAppHandle`）

**可去掉**：zed 的 `openharmony-ability`、`openharmony-ability-derive`（+ 视宏改法 `napi-ohos`/`napi-derive-ohos`）；gpui 的 `openharmony-ability`。

**必须保留**：`napi-build-ohos`（build-dependency）+ `zed/build.rs` 的 `napi_build_ohos::setup()`——NAPI 模块注册必须在生成 cdylib 的 crate（zed）的 build.rs 里，属**构建层**，无法 re-export。依赖隔离到"运行时"层面，构建层留在 zed。

### 备选方案 A（更彻底，不采用）

入口整体下沉到 gpui_ohos（`#[ability]` 在 gpui_ohos 用），zed 只注册启动回调，完全不接触 `OpenHarmonyApp` 类型。但需验证 NAPI 导出归属（gpui_ohos 作为 rlib 链接进 zed cdylib 的 `#[napi]` 注册）、处理依赖环/注册时序（`set_launcher` 必须先于 ArkTS `init`），改动大、风险高。

### 风险

- gpui `Platform` trait 签名改动是 breaking，但 `set_ohos_app` 唯一真实实现者是 `OhosPlatform`（gpui_ohos），其余平台走默认空实现，风险低。注意 `#[cfg(target_env = "ohos")]` 门控保持。
- derive 宏绝对路径改参数化需同步 gpui_ohos re-export。
- 文档同步：`crates/zed/ohos/README.md`、`鸿蒙移植分析.md`、`.claude/skills/zcoder-codemap/SKILL.md`。
