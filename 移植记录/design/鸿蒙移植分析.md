## 0 结论摘要（先说结果）

**结论一：Zed 具备移植到 OHOS 的可行性，且比 warp 的移植门槛更低。**

理由有四条：

1. **UI 完全自绘**：Zed 使用自研 GPUI 框架，UI 不依赖任何操作系统原生控件，满足可行性前提 0（UI 层可整体复用）。
2. **已有跨平台抽象层**：`crates/gpui/src/platform.rs` 定义了完整的 `Platform` trait（本地版本约 2900 行），`crates/gpui_platform/src/gpui_platform.rs` 的 `current_platform()` 是平台分发总入口。OHOS 只需新增一个平台实现并挂到分发函数上。
3. **已有现成 OHOS 平台实现可抄**：`richerfu/zed` fork 已实现了完整的 `gpui_ohos` crate（约 13 个文件，覆盖 `Platform` / `PlatformWindow` / `PlatformTextSystem` / 渲染 / 字体 / 调度 / 窗口），`ohos-rs/gpui-template` 演示了完整的 ArkTS 工程接入方式。这两者是「从零开始」与「站在别人肩膀上」的差别。
4. **渲染与字体走纯 Rust 路径**：Zed 用 wgpu 29（官方已内置 GL 后端，无需像 warp 那样 fork wgpu 加 OHOS 分支），字体用 cosmic-text + swash + fontdb（纯 Rust，无需 warp 的 Drawing API 单字形光栅化）。这两块是 warp 移植中最重的两块，Zed 的处境明显更好。

**结论二：但 Zed 不能直接套用 fork 的 diff，必须按本仓库的新版 API 面重新落地。**

fork 的 `gpui/src/platform.rs` 只有 1998 行，本仓库是 2900 行。本仓库的 `Platform` trait 多了 `gestures()`、`insets()`、`on_insets_changed()`、`set_back_handler()`、`show_soft_keyboard()`、`hide_soft_keyboard()`、`text_input_state_changed()`、`on_app_lifecycle()`、`on_memory_warning()` 等 mobile 平台方法。fork 的 `OhosPlatform` 实现在这些方法上缺失，需要按新版 trait 补全。好消息是：这些方法大多有默认空实现，且 fork 的 `window.rs` 已经在处理虚拟键盘、IME、焦点、生命周期事件，新增方法可以直接映射到现有事件处理逻辑上。

**结论三：Zed 应用层（`crates/zed`）才是真正的硬骨头，GPUI 平台层只是入场券。**

GPUI 平台层解决「窗口能显示、能渲染、能输入」的问题。但 Zed 是完整 IDE：它依赖 `std::process::Command` 启动 git / node / language server / extension host（沙箱禁 fork/exec，需绕行）、依赖文件系统读写（沙箱限 filesDir/cacheDir/tempDir，需映射）、依赖网络（部分可用）、依赖剪贴板（读受限）、依赖终端 PTY（无本机 PTY，需 SSH 桥或降级）。这些应用层能力 warp 全部踩过坑并有成熟解法（第 04/05/17/18 章），是本移植的真正工作量所在。

**结论四：gpui-template + fork 能省掉的是「平台接入」这一整块，估约占 GPUI 层工作量的 70% 以上。**

- NAPI / TSFN / XComponent 桥接：完全由 `openharmony-ability` crate 自动生成（`#[napi]` / `#[ability]` 宏），ArkTS 侧只需一个继承 `RustAbility` 的 `EntryAbility` 和默认页面。对比 warp 手写 `libentry.so` + `libwarp.so` 双 .so、手写 C++ FFI、dlsym 手动拉起——这是数量级的差异。
- 字体系统：`OhosTextSystem` 用 cosmic-text + swash + fontdb 扫描 `/system/fonts` 等目录 + `HarmonyOS Sans` 回退，几乎与 Linux 桌面路径一致。对比 warp 的 FontParser 枚举 + Drawing API 光栅化 + 像素格式修复——省掉一整章工作量。
- 渲染 surface：fork 的 `WgpuRenderer` 直接用 `wgpu::SurfaceTargetUnsafe::RawHandle` + `create_surface_unsafe`，靠 `HasWindowHandle` / `HasDisplayHandle`（fork 的 `OhosWindow` 实现了，返回 `RawWindowHandle::OhosNdk`）。对比 warp fork wgpu 改 `egl.rs`——省掉依赖库 fork 的维护负担。

**结论五（历史结论）：当时的产品名为 zcoder；现已改名为 HiCodeer。** 本目录代码库是 Zed（crate/二进制名保留 zed），当时移植到 OHOS 的产品名定为 **zcoder**，并判断「只改用户可见命名」：HAP 应用名、label、显示名用 zcoder；`moduleName`（与 `libzed.so` 库名强绑定）、crates/zed、二进制名、`paths::APP_NAME` 等底层技术标识保持不变。

**2026-09-22 现状**：产品名已是 **HiCodeer**，且 `moduleName` 与 native 库名也一并改为
`hicodeer` / `libhicodeer.so`——即"底层技术标识不变"这一条在后来的改名中已被推翻；
`crates/zed`、二进制名与 `paths::APP_NAME` 仍保留 `zed`。

## 1 移植可行性分析

### 1.1 软件性质

Zed 是开源的跨平台代码编辑器，核心由 Rust 编写：

- **构建系统**：Cargo workspace，根 `Cargo.toml` 的 `[workspace] members` 列出约 240 个 crate；`default-members = ["crates/zed"]`（根 `Cargo.toml` 第 265 行）。
- **UI 框架**：自研 GPUI（`crates/gpui` + `crates/gpui_platform` + `crates/gpui_macos` / `gpui_linux` / `gpui_windows` / `gpui_web` / `gpui_wgpu`）。
- **程序入口**：`crates/zed/src/main.rs` 的 `fn main()`。
- **平台抽象**：`crates/gpui/src/platform.rs` 的 `trait Platform`、`trait PlatformWindow`、`trait PlatformDisplay`、`trait PlatformTextSystem`、`trait PlatformDispatcher`、`trait PlatformAtlas`；分发入口在 `crates/gpui_platform/src/gpui_platform.rs` 的 `current_platform()`。

### 1.2 可行性前提对照

第 00 章方法论要求满足「已有跨平台抽象层」或「结构清晰、可新增适配层」任一：

- **满足**：Zed 有完整的跨平台抽象层（`Platform` trait + `current_platform()` 分发）。GPUI 已经支持 macOS / Windows / Linux / Web 四个平台，OHOS 是第五个 `cfg` 分支。迁移路径与 fork 已验证的一致：新增 `gpui_ohos` crate 实现 `Platform` trait，在 `current_platform()` 加 `#[cfg(target_env = "ohos")]` 分支。

### 1.3 UI 自绘确认

Zed 的 UI 完全由 GPUI 自绘：窗口内容、标题栏、面板、编辑器全部由 GPUI 的 scene graph + wgpu 渲染。不依赖系统 UI 控件。`WindowOptions`、`WindowParams`、`Scene`、`Draw` 等抽象与平台解耦，OHOS 平台只需提供 surface（XComponent 关联的 `OH_NativeWindow`）即可。**UI 层可整体复用**。

### 1.4 与 warp 的差异（Zed 反而更容易的点）

- **渲染后端**：warp 时代 wgpu 无 GL 后端，需 fork wgpu 在 `wgpu-hal/src/gles/egl.rs` 加 `OhosNdk` 分支。Zed 用 wgpu 29.0.4（根 `Cargo.toml` 第 900 行），官方已内置 `Backends::GL`，且 `crates/gpui_wgpu/Cargo.toml` 已启用 `webgl` feature。fork 的 `WgpuContext::new()`（`zed-ohos-gpui/src/ohos/wgpu_context.rs`）默认 `Backends::GL`，直接用官方 wgpu 即可，**无需 fork wgpu**。
- **字体系统**：warp 用 font-kit（依赖 fontconfig/FreeType），OHOS 无这两者，被迫走 `FontParser` + Drawing API 光栅化（第 09/10/11 章）。Zed 桌面渲染路径用 cosmic-text 0.19 + swash（纯 Rust，不依赖系统字体库），fork 的 `OhosTextSystem` 直接复用 cosmic-text 的 fontdb + SwashCache，**无需 Drawing API**。
- **NAPI 桥接**：warp 手写两 .so + C++ FFI + TSFN。Zed 生态直接用 `openharmony-ability` crate，NAPI 绑定由宏自动生成。

## 2 编码规范

移植新增代码必须遵循 Zed 原有的编码规范，不形成两套风格。从 `CLAUDE.md`（仓库根 `CLAUDE.md` 为 `AGENTS.md` 的符号链接，指向 `.rules`）与代码实际风格提取：

- **命名**：函数名、文件名、模块名使用全名，禁止简写（与 skill 规则一致，也是 Zed 自身惯例，见 `collections`、`fuzzy` 等 crate 的函数命名）。
- **错误处理**：避免 `unwrap()`，用 `?` 传播错误；禁止 `let _ =` 静默丢弃 fallible 操作；用 `.log_err()` 处理需要可见性但不阻断的错误。见仓库 `CLAUDE.md` 的 Rust coding guidelines。
- **上下文参数约定**：GPUI 中 `cx` 是上下文参数，位于参数列表最后；`window` 在 `cx` 之前（`&mut Window` / `&mut App` 等签名）。
- **注释**：不写总结性注释，只为「为什么这样写」的非显然原因写注释。
- **模块文件**：不创建 `mod.rs`，用 `src/some_module.rs`；新 crate 的 `[lib] path` 用描述性名称（如 `gpui_ohos.rs`）。
- **变量名**：用全词，不用 `q` 这类缩写。

新增 OHOS 代码应放在 `crates/gpui_ohos/`（新 crate）与 `crates/zed_ohos/`（若有应用层专属逻辑），遵循「路径含 ohos 可修改」的纪律。

## 3 日志系统

### 3.1 Zed 现有日志系统

Zed 用 `zlog` / `ztracing` crate（`crates/zlog`、`crates/ztracing`）封装的 `log` facade。入口在 `crates/zed/src/main.rs`：

- `zlog::init()`（main.rs 第 293 行）初始化日志。
- `stdout_is_a_pty()` 为真时 `zlog::init_output_stdout()`，否则 `zlog::init_output_file(paths::log_file(), Some(paths::old_log_file()))`（第 295-303 行）——**写日志文件**。
- `log::info!` / `log::warn!` / `log::error!` 遍布全仓库。

### 3.2 OHOS 约束与改造

OHOS 沙箱禁止在系统目录写文件，无 syslog/journald，日志必须投递 hilog（附录 A 第 06 章）。Zed 的 `zlog` 写文件路径在 OHOS 上不可用（`paths::log_file()` 会落到沙箱不可写位置，或写进 filesDir 但无系统日志聚合）。改造方案：

- 参考 warp `warp/crates/warp_logging/src/ohos.rs` 的 `OhosLogger`：实现 `log::Log` trait，在 `log()` 里把级别映射成 `LOG_DEBUG/INFO/WARN/ERROR` 并调 `OH_LOG_Print`（或 `ohos_hilog_binding` 的 `log::init_once`，gpui-template 已用此方式）。
- 在 `zlog` 的 OHOS 分支跳过文件落盘，只走 hilog。需要给 `zlog` / `ztracing` 加 `#[cfg(target_env = "ohos")]` 分支，或用 feature 开关。注意 fork 的 Cargo.lock 里 `zlog`、`ztracing` 也在 fork 涉及列表中，说明 fork 已经处理过日志适配，可以直接参考其 diff（通过 GitHub 对比 f1529bc6 与上游同名文件即可得到准确改动，避免重推）。

### 3.3 日志开关

Zed 用编译期 feature + 运行时 env var 组合。`zlog` 的 level 通过 `LevelFilter` 控制。OHOS 上应按 warp 纪律：error/warn 所有版本打印，info/debug 调试完成后删除或降级。

## 4 特性开关

Zed 的特性开关机制：

- **编译期 cfg**：大量 `#[cfg(target_os = "macos")]` / `#[cfg(target_os = "windows")]` / `#[cfg(any(target_os = "linux", target_os = "freebsd"))]`。OHOS 的 `target_os` 是 `linux`，必须用 `#[cfg(target_env = "ohos")]` 区分（见第 19 章）。
- **feature flag**：`feature_flags` crate（`crates/feature_flags`）提供运行时开关，`crates/feature_flags/src/feature_flags.rs` 中定义各类 feature。
- **env var**：`ZED_HEADLESS`、`ZED_DEVICE_ID`（fork 的 `WgpuContext` 已读）、`ZED_STATELESS` 等。

OHOS 适配遵循「平台绑定、无法运行时收敛的用 cfg；可在运行时决策的用 FeatureFlag / env var」。特别是：凡是 `#[cfg(target_os = "linux")]` 且 OHOS 需要不同行为的点，必须改成 `#[cfg(all(any(target_os = "linux", target_os = "freebsd"), not(target_env = "ohos")))]` 或单独加 `#[cfg(target_env = "ohos")]` 分支（第 19 章成对包裹模式）。

## 5 设计文档（原项目文档提炼）

Zed 仓库根目录文档：

- `README.md`（本仓库是镜像，内容极简）。
- `CONTRIBUTING.md`：开发者贡献指南，强调用 `./script/clippy` 而非 `cargo clippy`（仓库 `CLAUDE.md` 的 build guidelines 也重申）。
- `.rules`（`AGENTS.md` / `CLAUDE.md` / `GEMINI.md` 的符号链接目标）：本仓库的 AI 协作规则，含「Pull request hygiene」「Crash Investigation」「Rules Hygiene」等。移植新增代码必须遵守这些规则：PR 标题不用 conventional prefix、必须带 `Release Notes:` 段等。
- `docs/`：设计文档目录。

移植纪律（第 00 章移植原则）与 Zed 自身规则结合：

1. **提取原项目原则**：已提取（第 2 节编码规范、本节文档规则）。

## 6 代码架构分析

### 6.1 多操作系统框架设计（5.1）

Zed 的跨平台框架是三层：

- **`crates/gpui`**（核心框架）：定义 `Platform` trait 与全部平台无关的 UI 抽象（`App`、`Window`、`Entity`、`Scene`、`Styled` 等）。不直接依赖任何平台 API。
- **`crates/gpui_platform`**（分发层）：极薄 crate，只做 `current_platform()` 的 `cfg` 分发（见 `crates/gpui_platform/src/gpui_platform.rs` 第 57-81 行）。
- **平台实现 crate**：`gpui_macos` / `gpui_windows` / `gpui_linux` / `gpui_web`。每个实现 `Platform` trait 及配套类型。
- **渲染实现**：`gpui_wgpu`（wgpu 渲染器，跨平台复用）。
- **应用层**：`crates/zed` 及各功能 crate（editor、workspace、project、terminal 等），只依赖 `gpui` 抽象，不依赖具体平台。

OHOS 的接入点：新增 `crates/gpui_ohos` crate（对应 fork 的 `gpui_ohos`），在 `gpui_platform` 的 `current_platform()` 加 `#[cfg(target_env = "ohos")]` 分支。这正是 fork 的做法（`zed-ohos-gpui/gpui_platform.rs` 第 36-39 行）。

### 6.2 适配总入口（5.2）

总入口是 `crates/gpui_platform/src/gpui_platform.rs` 的 `current_platform(headless) -> Rc<dyn Platform>`。fork 的版本在第 22-48 行新增：

```
#[cfg(target_env = "ohos")]
{
    gpui_ohos::current_platform(headless)
}
```

并把 Linux 分支改为 `#[cfg(all(not(any(target_os = "macos", target_os = "windows")), not(target_env = "ohos")))]` 排除 OHOS。Zed 应用层 `crates/zed/src/main.rs` 的 `build_application()`（第 86-93 行）调用 `gpui_platform::current_platform(false)`，无需改动即可命中 OHOS 分支。

### 6.3 适配总接口定义（5.3）

`Platform` trait（`crates/gpui/src/platform.rs`）定义的平台能力清单（本地新版，约 2900 行）：

- **执行器**：`background_executor()`、`foreground_executor()`、`PlatformDispatcher`（`is_main_thread` / `dispatch` / `dispatch_on_main_thread` / `dispatch_after` / `spawn_realtime` / `now`）。
- **文本系统**：`text_system()` → `PlatformTextSystem`（`add_fonts` / `all_font_names` / `font_id` / `font_metrics` / `typographic_bounds` / `advance` / `glyph_for_char` / `glyph_raster_bounds` / `rasterize_glyph` / `layout_line` / `recommended_rendering_mode`）。
- **生命周期**：`run()` / `quit()` / `restart()` / `activate()` / `hide()` / `hide_other_apps()` / `unhide_other_apps()` / `on_quit()` / `on_reopen()` / `on_app_lifecycle()` / `on_memory_warning()`。
- **显示**：`displays()` / `primary_display()` → `PlatformDisplay`（`id` / `uuid` / `bounds` / `visible_bounds` / `default_bounds`）。
- **窗口**：`open_window()` → `Box<dyn PlatformWindow>`；`PlatformWindow` 接口（`bounds` / `content_size` / `resize` / `scale_factor` / `set_input_handler` / `on_request_frame` / `on_input` / `on_resize` / `draw` / `sprite_atlas` / `gpu_specs` / `update_ime_position` / `set_virtual_keyboard_visible` / `insets` / `set_back_handler` / `show_soft_keyboard` / `hide_soft_keyboard` / `text_input_state_changed` 等）。
- **屏幕捕获**：`is_screen_capture_supported()` / `screen_capture_sources()`。
- **URL**：`open_url()` / `on_open_urls()` / `register_url_scheme()`。
- **文件对话框**：`prompt_for_paths()` / `prompt_for_new_path()` / `can_select_mixed_files_and_dirs()` / `reveal_path()` / `open_with_system()`。
- **菜单**：`set_menus()` / `set_dock_menu()` / `on_app_menu_action()` / `on_will_open_app_menu()` / `on_validate_app_menu_command()`。
- **剪贴板**：`read_from_clipboard()` / `write_to_clipboard()` / `read_from_primary()` / `write_to_primary()`。
- **凭据**：`write_credentials()` / `read_credentials()` / `delete_credentials()`。
- **键盘**：`keyboard_layout()` / `keyboard_mapper()` / `on_keyboard_layout_change()`。
- **通知**：`show_system_notification()` / `dismiss_system_notification()` / `on_system_notification_response()`。

OHOS 平台实现（fork 的 `OhosPlatform` + 待补方法）必须实现以上接口。**注意**：fork 版本基于旧 trait，缺少本仓库新版的 `gestures()`、`insets()` 相关、`set_back_handler()`、`show_soft_keyboard()`、`hide_soft_keyboard()`、`text_input_state_changed()`、`on_app_lifecycle()`、`on_memory_warning()` 等。这些新版方法均有默认实现，多数可直接采用默认（`insets()` 返回默认、`set_back_handler` 默认空、`show_soft_keyboard` 默认空），但为满足 Zed 功能（虚拟键盘、IME 光标、返回键），应当用 fork 的 `window.rs` 中已有的 `show_keyboard_if_needed` / `hide_keyboard_if_needed` / `keyboard_inset_for_overlap` 逻辑补全。

### 6.4 编译隔离与运行分支（5.4）

Zed 本体目前**不含任何 `target_env = "ohos"` 代码**（已用 `grep -rln 'target_env = "ohos"' crates/` 验证为零命中）。需要新增的编译隔离点主要分三类：

**第一类：`crates/gpui_platform/src/gpui_platform.rs`**
- `current_platform()` 加 ohos 分支（fork 已验证）。

**第二类：`crates/gpui/src/platform.rs`**
- `Platform` trait 加 `set_ohos_app()`（fork 做法：`#[cfg(target_env = "ohos")] fn set_ohos_app(&self, _app: OpenHarmonyApp) {}` 带默认空实现，`OhosPlatform` override）。
- Linux 专属方法（`read_from_primary` / `write_to_primary`）在 OHOS 下应排除或独立实现（fork 用 `not(target_env = "ohos")` 排除）。
- `PlatformWindow` 的 Linux 专属方法（`inner_window_bounds` / `request_decorations` / `show_window_menu` / `start_window_move` / `start_window_resize` / `set_app_id` 等）大多有默认实现，OHOS 不需要的用默认空。

**第三类：`crates/zed` 应用层与功能 crate**
- `paths` crate（`crates/paths/src/paths.rs`）：目录定位需映射到沙箱 filesDir/cacheDir/tempDir（第 05 章）。这是**大改动面**，参考 warp `warp/crates/warp_core/src/paths.rs` 的 `ohos_files_dir` / `ohos_cache_dir` / `ohos_temp_dir`。
- `crates/zed/src/main.rs`：入口改造（见第 7 节）。
- 终端（`crates/terminal` / `crates/terminal_view`）：PTY 依赖（见第 10 节进程/线程）。
- 进程创建（git、node、language server、extension host）：`std::process::Command`（见第 10 节）。
- `zlog` / `ztracing`：日志重定向（第 3 节）。

**运行时操作系统分支**：Zed 用 `std::env::consts::OS`（main.rs 第 505 行）拼 user agent；`OperatingSystem` 枚举在 `crates/zed` 无独立实现（与 warp 不同，warp 有 `warpui_core::platform::OperatingSystem`）。OHOS 上 `std::env::consts::OS` 返回 `"linux"`，需注意 user agent 语义（`Zed/x (linux; aarch64)`），一般可接受。

### 6.5 各平台适配对照（5.5）

- **macOS**（`gpui_macos`）：用 AppKit + Metal（`metal_renderer`），功能最全（菜单、dock、tabbed windows、traffic light、Find pasteboard）。
- **Windows**（`gpui_windows`）：用 Win32 + D3D，有 `get_raw_handle()` 返回 HWND。
- **Linux**（`gpui_linux`）：用 winit（x11/wayland）+ `gpui_wgpu`（wgpu），有 layer_shell 支持。
- **Web**（`gpui_web`）：WASM + WebGL/webgpu，`run_embedded` 模式（`Platform::run` 返回，宿主驱动循环）——**这个模式与 OHOS 最接近**。

OHOS 平台实现应重点参照 **`gpui_web` 的 `run_embedded` 模式**（OHOS 的 `Platform::run` 不能阻塞，需把 `OpenHarmonyApp::run_loop` 当作宿主事件循环）和 **`gpui_linux` 的 wgpu 渲染路径**（fork 的 `OhosTextSystem` / `WgpuRenderer` 就是从 `gpui_wgpu` 演化来的）。

## 7 main 函数入口分析

### 7.1 原 main 执行顺序（`crates/zed/src/main.rs`）

1. `STARTUP_TIME.get_or_init(...)` 记录启动时间。
2. `sandbox::run_sandbox_launcher_if_invoked()`（Linux sandbox helper，OHOS 无此需求，可跳过）。
3. `util::prevent_root_execution()`（unix）。
4. `Args::parse()`（clap 解析命令行）。
5. `init_paths()`（`crates/paths` 创建 8 个目录）。
6. `zlog::init()` + 日志输出初始化。
7. `ztracing::init()`。
8. 版本信息、rayon 线程池、crash handler。
9. `build_application()`（`gpui_platform::current_platform(false)`）→ `.with_assets(Assets)`。
10. 数据库、session、OpenListener 初始化。
11. `app.run(...)` 内：大量 `*::init(cx)`（settings、client、language、theme、editor、workspace、terminal、extension host 等约 60 个），最后 `initialize_workspace(app_state, cx)` + `cx.activate(true)`。

### 7.2 OHOS 融合方案

OHOS 无 `main()`，HAP 的入口是 ArkTS `EntryAbility`。参考 gpui-template 的 `src/lib.rs`：

- Rust 侧用 `#[openharmony_ability_derive::ability]` 宏标注入口函数，签名 `pub fn openharmony_app(app: OpenHarmonyApp)`。
- 函数内调用 `Application::with_platform(gpui_platform::current_platform(false))`（或 fork 的 `Application::new()` + `.with_ohos_app(app)`）。
- `Platform::run`（fork 的 `OhosPlatform::run`）内部 `app.run_loop(...)` 注册事件回调，`on_finish_launching` 在 `Event::SurfaceCreate` 时触发，窗口在此时创建。
- 原 `main()` 中「需要保留」的初始化（settings、client、language、theme 等）要搬进 `app.run(...)` 的回调里；「需要跳过」的（clap 解析、`init_paths` 的目录创建、crash handler 的 socket 通信、`--printenv` 等 CLI-only 分支）按 OHOS 分支剔除或改写。

关键点：OHOS 上 `Application::run()` 不能阻塞（宿主是 ArkTS 事件循环）。fork 的 `gpui/app.rs` 在 `run()` 末尾加了 `#[cfg(target_env = "ohos")] { _ = Box::leak(Box::new(self)); }`（`zed-ohos-gpui/gpui_app.rs` 第 192-195 行），防止 `Application` 在 `Platform::run` 返回后析构。Zed 移植必须保留这个 leak（或改用手持 handle 的方式）。

### 7.3 main 对操作系统的依赖分析

- **文件系统**：`init_paths()` 创建 8 个目录（config/extensions/languages/debug_adapters/database/logs/temp/hang_traces）。OHOS 沙箱只能写 filesDir/cacheDir/tempDir → 需把 `paths` crate 的目录定位重映射（第 05 章，warp `set_ohos_environment` 注入 HOME/TMPDIR）。
- **进程**：启动 language server、git、node 需要 `Command`（沙箱禁 fork）→ 见第 10 节。
- **网络**：`Client::production`、`ReqwestClient` 走 HTTP/HTTPS → OHOS 可用，无需大改。
- **凭据**：`write_credentials` / `read_credentials` → OHOS 无 Keychain，需降级（fork 的 `OhosPlatform` 已返回 `Err`/`None`）。
- **剪贴板**：读受限 → PasteButton 或降级（第 17 章）。
- **通知**：`show_system_notification` → 可经 NAPI 桥接 ArkTS（第 17 章），fork 未实现，需补。

## 8 代码架构：GPUI 平台层适配细节（A/B 框架）

### 8.1 fork 的 `gpui_ohos` crate 结构与可搬移性评估

> **现状注（2026-09-22）**：本节描述的是 2026-08-16 从 `zed-ohos-gpui/`（fork 快照）拉取时的
> 结构与行数（如 `platform.rs` 431 行、`window.rs` 1279 行）。当前 `crates/gpui_ohos` 已自行
> 大幅演进（`platform.rs` 约 31 KB、`window.rs` 约 119 KB，另有 `wgpu_context.rs` /
> `keycodes.rs` 等），逐接口的实现状态见 `GPUI平台接口适配清单.md`。本节保留作"起点"记录。

已拉取到 `zed-ohos-gpui/`，结构如下：

- `src/gpui_ohos.rs`：`#![cfg(target_env = "ohos")]` + `mod ohos;` + `pub use ohos::current_platform;`。
- `src/ohos.rs`：`mod` 声明 + `pub fn current_platform(headless) -> Rc<dyn Platform>`（构造 `OhosPlatform`）。
- `src/ohos/platform.rs`（431 行）：`OhosPlatform`，实现 `Platform` trait。核心：`run()` 用 `app.run_loop` 注册事件回调；`handle_ohos_event()` 先跑 foreground tasks、再在 `SurfaceCreate` 时调 `on_finish_launching`、再把事件路由给所有存活窗口；`open_window()` 创建 `OhosWindow` 并立即 `initialize_renderer()`。
- `src/ohos/window.rs`（1279 行）：`OhosWindow` + `OhosWindowHandle`。事件处理（`SurfaceCreate` / `WindowResize` / `ContentRectChange` / `AvoidAreaChange` / `WindowRedraw` / `Input` / `GainedFocus` / `LostFocus` / `ConfigChanged` / `WindowDestroy` / `KeyboardEvent`）、键盘 inset 计算（`keyboard_inset_for_overlap` / `keyboard_overlap_from_avoid_area_device_px`，处理 Keyboard/System/SystemGesture/NavigationIndicator 四个 avoid area 并做区间并集）、触摸→鼠标/滚轮转换、IME 事件处理（`TextInputEvent` → `replace_text_in_range`，`EnterEvent` → 换行，`BackspaceEvent` → 删字符）。实现 `HasWindowHandle` / `HasDisplayHandle`（`window_handle()` 从 `app.native_window()` 取 raw handle，`display_handle()` 返回 `RawWindowHandle::ohos()`）。
- `src/ohos/text_system.rs`（647 行）：`OhosTextSystem`，基于 cosmic-text `FontSystem` + `SwashCache`。`ensure_system_fonts_loaded()` 扫描 `/system/fonts`、`/system/font`、`/vendor/fonts`、`/system_ext/fonts`、`/data/fonts` 五个目录；`load_family()` 按 `HarmonyOS Sans` 回退链匹配；`font_id()` 用 font-kit 的 `find_best_match` 打分；光栅化走 `SwashCache::get_image`。
- `src/ohos/dispatcher.rs`（180 行）：`OhosDispatcher`，`dispatch` 直接 `std::thread::spawn` 跑后台任务，`dispatch_on_main_thread` 进 `PriorityQueueSender`，`dispatch_after` 用 Condvar + BinaryHeap 定时器堆，定时到用 `OpenHarmonyWaker` 唤醒主线程。
- `src/ohos/display.rs`（67 行）：`OhosDisplay`，`bounds()` 从 `app.content_rect()` 换算（除以 `app.scale()`）。
- `src/ohos/keyboard.rs`（31 行）：`OhosKeyboardLayout` / `OhosKeyboardMapper`，当前是 no-op 透传——**这是待补缺口**（见 8.3）。
- `src/ohos/wgpu_context.rs`（187 行）：`WgpuContext`，`new()` 默认 `Backends::GL`，`#[cfg(target_env = "ohos")]` 下禁用 dual_source_blending。
- `src/ohos/wgpu_renderer.rs`（1675 行）：`WgpuRenderer`，`create_surface_unsafe` 从 raw-window-handle 建 surface，`PresentMode::Fifo`，完整管线（quads/shadows/paths/underlines/sprites）。
- `src/ohos/wgpu_atlas.rs`（320 行）：`WgpuAtlas`。
- `src/ohos/shaders.wgsl`（1579 行）。

**可搬移性结论**：`platform.rs` / `window.rs` / `dispatcher.rs` / `display.rs` / `wgpu_context.rs` / `wgpu_renderer.rs` / `wgpu_atlas.rs` / `shaders.wgsl` 可直接搬入本仓库的 `crates/gpui_ohos`，但需按新版 `Platform` trait 补全缺失方法（`gestures`、`insets`、`on_app_lifecycle`、`set_back_handler` 等）并适配新版 API 签名（`RequestFrameOptions`、`WindowParams` 等可能变化）。`text_system.rs` 需重点核对 `font-kit` 依赖（见 8.3）。`keyboard.rs` 需重写。

### 8.2 fork 的 `gpui` / `gpui_platform` 改动

- `crates/gpui_platform/src/gpui_platform.rs`：`current_platform()` 加 ohos 分支（见 6.2）。
- `crates/gpui/src/platform.rs`：`Platform` trait 加 `set_ohos_app`（`#[cfg(target_env = "ohos")]` 默认空实现）。
- `crates/gpui/src/app.rs`：`Application::with_ohos_app()`（`#[cfg(target_env = "ohos")]`，调用 `platform.set_ohos_app(app)`）；`run()` 末尾 `Box::leak(self)`。
- `crates/gpui/Cargo.toml`：`[target.'cfg(target_env = "ohos")'.dependencies]` 加 `openharmony-ability`。

以上改动面极小（约 4 处），本仓库照搬时只需适配行号与签名。

### 8.3 待补缺口与风险点

- **键盘映射**（fork `keyboard.rs` 是 no-op）：OHOS 键码 → GPUI `Keystroke` 的映射需要实现。参考 warp `depends/winit/src/platform_impl/ohos/keycodes.rs` 与 `warp/crates/warpui/src/windowing/ohos/ohos_keymap.rs`（`ohos_keycode_to_warp_key` / `warp_key_to_ohos_keycode`）。注意 OHOS 键码来自 `openharmony_ability` 的 `InputEvent::KeyEvent`，需先确认该库是否暴露键码（fork 的 `window.rs` 只处理 Touch/IME，未处理硬件键盘 KeyEvent——**这是 Zed 编辑器最关键的输入缺口**，必须补）。
- **font-kit 依赖**：`gpui_ohos/Cargo.toml` 依赖 `font-kit`（zed-font-kit）且带 `source-fontconfig-dlopen` feature。OHOS 无 fontconfig，`source-fontconfig-dlopen` 可能在运行时找不到 libfontconfig 而崩溃或降级。**必须验证**：fork 的 `text_system.rs` 只用 font-kit 的 `properties`/`matching`（字体匹配打分），不实际加载 fontconfig——如果 zed-font-kit 在 `source-fontconfig-dlopen` 下懒加载失败有回退，则可用；否则应去掉该 feature 或改 feature。这是高优先验证项。
- **移动键盘 / IME 光标**：fork 有 `show_keyboard_if_needed` / `hide_keyboard_if_needed` / `keyboard_inset_for_overlap`，但 `update_ime_position` 是 no-op（`// There is no such thing on Windows.` 注释是笔误，OHOS 需要实现光标上报到 ArkTS 以定位候选框，参考 warp 第 13 章 TSFN 光标链路）。
- **剪贴板**：fork `read_from_clipboard` / `write_to_clipboard` 返回 `None` / 空实现。Zed 需要复制粘贴，必须补（第 17 章 PasteButton 或权限）。
- **系统通知 / 打开 URL / 文件选择器 / 凭据**：fork 全 no-op。Zed 的 `open_url`（打开链接）、`prompt_for_paths`（打开文件/目录）、通知均会用到，需按第 17 章 + warp `ohos_delegate.rs` 补齐。
- **VSync / 帧循环 / 遮挡感知**：fork 的渲染靠 `Event::WindowRedraw`（ArkTS 的 `onXComponentRedraw`）触发 `on_request_frame`，没有 warp 第 08 章的 `OH_NativeVSync` 按需帧循环 + 遮挡门闸。Zed 的动画/光标闪烁/平滑滚动可能依赖稳定的帧节奏。**这是性能关键**，建议移植 warp 的 `OH_NativeVSync` 方案（`init_vsync` / `ensure_vsync_running` / `stop_vsync` / `PENDING_REDRAW` / `WINDOW_VISIBLE` / `is_fully_occluded`）。
- **窗口尺寸单一来源**：fork 用 `content_rect()` 初始化 bounds、`WindowResize` 事件更新。warp 第 14 章强调「尺寸统一从 `surface_size()`（XComponent）获取」，避免标题栏/内容区尺寸错位。fork 的 `initialize_renderer` 已用 `content_rect`，需与 warp 经验对照确认无 84px 偏移类问题。

## 9 受保护文件纪律（第 19 章落地到 Zed）

Zed 仓库中「全路径不含 ohos」的文件属于受保护文件。移植时：

## 10 进程 / 线程分析与 OHOS 约束

### 10.1 线程模型

- **UI/主线程**：GPUI 单前台线程执行所有 UI 渲染与 Entity 更新。OHOS 上这是 ArkTS UI 线程（或由 `OpenHarmonyApp::run_loop` 驱动的线程），fork 用 `OhosDispatcher` 把 main-thread 任务投进 `PriorityQueueReceiver`，由 `run_loop` 事件回调消费。
- **后台线程**：GPUI 的 `cx.background_spawn` 任务、rayon 线程池（main.rs 第 323-328 行，`available_parallelism/2`）、tokio（`gpui_tokio`）、LSP 与 extension host 子进程。
- **进程**：Zed 大量使用子进程：
  - git（`git` crate 的 `Command`）
  - node（`node_runtime` 下载并执行）
  - language server（`language` crate，`LspStore` 启动 LSP 二进制）
  - extension host（`extension_host`，spawn 一个 `zed-extension` 进程）
  - 终端（`terminal` crate，PTY + shell）
  - auto_update、crash handler（socket 通信）

### 10.2 OHOS 约束对照（附录 A）

- **fork/exec 禁止**（第 04 章）：`std::process::Command::spawn()` 返回 `EPERM`。Zed 的 git / node / LSP / extension host 全部依赖此 → **这是应用层最大的硬约束**。
  - 规避选项：
    1. **线程替代**：纯计算型子进程改线程。
    2. **原生子进程**：`OH_Ability_StartNativeChildProcess`（warp 的 `ShellBridgeMain` 模式），把 git/LSP/extension host 做成同包 .so 的原生入口，用 `NativeChildProcess_Args` / `NativeChildProcess_FdList` 传参。
    3. **SSH 桥**（warp 第 18 章）：git 与 shell 经 SSH 发往 PC/VM。对 IDE 场景，SSH 桥接成本高，需评估「Zed 的远程开发」是否天然可用（Zed 有 `RemoteConnectionOptions::Ssh`，本身就是 SSH 远程协议——**这可能反而是优势**：OHOS 端 Zed 可以直接连到开发机的 Zed server）。
  - 建议：git 与 shell 走 SSH 桥（复用 warp `ohos_shell_bridge.rs` 的 `OhosCommand` / `OhosPtyBridge` 模式），language server 走原生子进程或线程内嵌，extension host 评估线程内嵌。
- **openpty 禁止**（第 04/18 章）：Zed 终端需要 PTY。无本机 PTY → SSH 桥到 VM bash（warp `OhosPtyBridge::spawn_via_socket`）或**降级为不使用内嵌终端**（保留接口，UI 显示「终端不可用」的降级提示，符合「显式降级」纪律）。
- **文件系统沙箱**（第 05 章）：只可写 filesDir/cacheDir/tempDir。`paths` crate 的 config/extensions/languages/debug_adapters/database/logs 目录全部映射到沙箱内。
- **剪贴板读受限**（第 17 章）：PasteButton 或权限。
- **后台冻结**（第 17 章）：TASK_KEEPING 持续任务保活（SSH/协作连接）。
- **网络**：可用，无需大改。
- **无 fontconfig/FreeType**：已解决（cosmic-text 纯 Rust，见 1.4）。
- **NAPI 线程限制**（第 15 章）：已由 `openharmony-ability` 的 TSFN 封装解决。

### 10.3 与 warp 的复用对照表

以下 warp 代码可直接移植/借鉴到 Zed：

- 日志：`warp/crates/warp_logging/src/ohos.rs`（`OhosLogger` / `log_redirect_2_hilog`）→ 移植到 Zed 的 `zlog` OHOS 分支。
- 文件沙箱：`warp/app/src/platform/ohos/ohos_entry.rs`（`set_ohos_environment`）→ 映射 Zed `paths` 目录。
- 文件选择器：`warp/crates/warpui/src/windowing/ohos/ohos_delegate.rs`（`OhosFilePicker` / `map_vm_path_to_local` / `request_authorization`）→ 映射 Zed `prompt_for_paths` / `reveal_path`。
- 进程/PTY：`warp/app/src/platform/ohos/ohos_shell_bridge.rs`（`OhosPtyBridge` / `OhosCommand` / dlsym 加载器）→ 映射 Zed git/shell 执行。
- 输入：`depends/winit/src/platform_impl/ohos/keycodes.rs` + `warp/crates/warpui/src/windowing/ohos/ohos_keymap.rs` → 补 Zed OHOS 键盘映射。
- IME：`warp/app/src/platform/ohos/ohos_entry.rs`（`ohos_ime_insert_text` 等）→ 补 Zed IME（fork 已部分处理）。
- 窗口：`depends/winit/src/platform_impl/ohos/mod.rs`（`OhosEventQueue` / 尺寸单一来源 / 遮挡）→ 补 Zed 窗口事件。
- VSync：`depends/winit/src/platform_impl/ohos/mod.rs`（`init_vsync` / 按需帧循环）→ 补 Zed 帧循环。
- 系统能力：`warp/crates/warpui/src/windowing/ohos/ohos_delegate.rs`（光标、打开文件）→ 补 Zed 对应 Platform 方法。

**注意**：warp 的这些代码基于 winit + warpui，与 Zed 的 GPUI 抽象不同，不能整文件复制，需「按设计模式移植」（读对应章，吸收规避方案 + warp 位置 + 坑警示，用 GPUI trait 重写）。

## 12 风险与验证清单

- **font-kit `source-fontconfig-dlopen` 在 OHOS 上的行为**：高优先验证。若 zed-font-kit 加载 fontconfig 失败导致 panic，需改 feature。
- **硬件键盘事件**：`openharmony_ability` 是否暴露 `InputEvent::KeyEvent`？fork 的 window.rs 未处理，若库已暴露需补映射，若未暴露需给该库发 PR 或绕行（触屏输入法已可用，硬件键盘可后补）。
- **新版 API 签名差异**：fork 基于旧 Zed，`RequestFrameOptions` / `WindowParams` / `WindowAppearance` 等在本仓库可能字段不同，搬移时逐一核对编译错误。
- **NAPI 线程安全**：`OhosDispatcher::dispatch` 直接 `std::thread::spawn` 跑任务，若任务内触 NAPI 会 SIGABRT（第 15 章）。需确认 OpenHarmonyApp 的桥接已用 TSFN 封装（app.rs 的 `bridge()` / `main_thread()` 已封，风险较低，但 background_spawn 里的 NAPI 调用要审计）。
- **内存**：Zed 是重型 IDE，OHOS 设备（尤其手机）内存/屏幕限制，`default_bounds` 与 `window_min_size` 需按设备调整。
- **`Box::leak` 的替代**：fork 用 `Box::leak(self)` 防析构，长期内存泄漏 1 次（可接受），或用 `ApplicationHandle`（`run_embedded`）模式更优雅。
- **sandbox crate 阻塞（同步后新增）**：`main()` 的 `sandbox::run_sandbox_launcher_if_invoked()` 无 ohos gate，`crates/sandbox` 核心逻辑 `#[cfg(target_os = "linux")]` 在 ohos 下会被编译，可能成为 ohos 构建阻塞点，需单独处理（第 9 节受保护文件清单之外的新发现）。
- **settings_ui 的 cpal 依赖（同步后新增）**：本地 `settings_ui/src/pages/audio_input_output_setup.rs` 与 `audio_test_window.rs` 直接用 `cpal::DeviceId`，而同步后 cpal 只在非 OHOS 目标段启用，OHOS 编译会失败。需决策：排除这两个页面 / 按 feat 重写 / OHOS 排除 settings_ui crate。
- **pthread 符号桩（同步后新增）**：`lib.rs` 的 `pthread_mutexattr_setrobust`/`pthread_mutex_consistent` 返回 0（链接期符号覆盖，feat 原样），若依赖 robust mutex 的库真的用到会静默失败，需确认必要性。
- **编译工具链损坏（同步后新增）**：本环境 rustup 1.97.1 工具链损坏，无法执行 `cargo check`；全部同步改动未经编译验证，需在健康工具链下对 `crates/gpui`、`crates/zed` 做 ohos target 编译确认。

## 13 结论：gpui-template 对 Zed 移植到底省了什么

对照 warp（从零移植）与「有 gpui-template/fork 可用」两种情况，量化省下的部分：

1. **NAPI/TSFN/XComponent 桥接层**（warp 第 15 章，约 3-5 个文件：`service_tsfn.cpp` / `napi_init.cpp` / 双 .so 构建）：**省掉**。`openharmony-ability` 自动生成，ArkTS 侧只留 2 个文件（EntryAbility + 页面）。
2. **渲染 surface + GL 后端**（warp 第 07 章，fork wgpu 改 egl.rs）：**省掉 fork 依赖**。wgpu 29 官方 GL 后端 + fork 的 `WgpuRenderer` 直接可搬。
3. **字体系统**（warp 第 09/10/11 章，FontParser 枚举 + Drawing API 光栅化 + 缓存）：**大幅简化**。cosmic-text + swash 纯 Rust，fork 的 `OhosTextSystem` 已实现，仅需验证 font-kit 依赖。
4. **窗口/事件/生命周期桥接**（warp 第 14/16 章）：**已有基础**。fork 的 `OhosWindow` / `OhosPlatform` 处理了大部分事件与生命周期，需补 insets/back_handler/IME 光标。
5. **工程骨架**（`ohrs init` + ohos 目录 + build.rs）：**直接复用** gpui-template 的 `ohos/` 目录结构。

**未省下的（仍需按 warp 经验做的）**：文件沙箱（paths）、日志（zlog→hilog）、进程/PTY（git/LSP/终端/extension host）、剪贴板、系统通知、VSync 帧循环、键盘映射。这些是应用层 + 平台细节，warp 提供了成熟解法（见第 10.3 节复用对照表），但不是「拿来即用」，需按 GPUI 抽象重写。

总体判断：**gpui-template + richerfu/zed fork 把「GPUI 平台接入」这一整块（估计占 GPUI 层 70%+ 工作量）变成了「搬移 + 补缺口」，让 Zed 移植的主要矛盾从「怎么让窗口显示」转移到了「怎么让 IDE 的进程/文件/终端在沙箱里活下来」**。后者正是 warp 移植方法论最擅长的领域（第 04/05/17/18 章），也是本项目后续投入的重点。
